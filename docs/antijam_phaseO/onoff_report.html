Anti-jam milestone · Phase O · 2026-09-08

The on/off jammer, across every array we have

A stationary jammer that switches on and off, tested on all seven exported arrays and five target directions. The predictive algorithm built for exactly this case turned out never to be firing; this is the diagnosis, the repair, and an honest account of where the repair helps and where it does not.

Arrays 7 (5 testable, 2 degenerate) Cases 198 × 3 seeds Runs 1,782 closed-loop, 0 failed Gates 59/59 Coherence span 0.06 – 0.98

Verdict

01

The on/off algorithm was never actually running

Its anticipatory branch fired on at most 1.3% of steps, and never at all outside a narrow 10–15 s band. Two independent causes, both arithmetic rather than tuning. Repaired, it fires 1.4–4.7% of steps and presence error against the true duty cycle falls from 0.46 to 0.13.

02

Every array now runs; two of them can't be helped, and say so

A 1-element and a 2-element array previously crashed the whole stack. They now run, and the geometry check reports 11 of 35 (array, target) pairs as infeasible with a stated reason — no gain, or a main beam covering the sphere — rather than scoring them as failures.

03

The repair is not universally good, and I am not recommending it as a default yet

It gains +10.8, +9.6 and +4.5 points on three arrays and is neutral on two — but regresses ManyDipoles by 3.3, costing 3 passing cells. Every regression is at the fastest toggle period, and the cause is a release policy that fixing presence exposed for the first time.

What was tested, and how difficulty was made comparable

A stationary jammer at a fixed direction, switching on and off at 50% duty. Three axes were swept that no previous campaign had touched.

Target direction — never varied before

Every campaign to date fixed the target at (θ 90, φ 260). Measured across the seven arrays, quiescent directivity toward a target swings about 18 dB and the −3 dB beamwidth spans 24° to 120°. Target direction is a difficulty axis in its own right. On the mirror-degenerate array, (90, 260) is additionally the symmetry plane — that array's single most favourable target.

Separation in units of each array's own beam

A jammer 20° from the target is trivial for a 20-element array and inside the main lobe of a 6-element one. Separations are therefore set as multiples of a derived guard sector — half the wider beamwidth toward that target — so the same three numbers mean the same physical difficulty on every array.

The shipped guard_deg = 5 is wrong on every array. Derived per (array, target) it ranges 16° to 72.5°. The global constant was calibrated once, from one array's 15° beamwidth, and does not survive contact with a 120° beam. This is test infrastructure, applied identically to both arms, so it does not confound the comparison — but it invalidates the geometry of earlier campaigns that used the global value.

Result 1 — how close each array gets to its own potential

The score is the fraction of the run spent within 3 dB of a perfect-knowledge beamformer on that array, at that geometry. It asks "did we get what this aperture can give", not "did we hit an absolute number" — which is the right question when a 1-element array and a 20-element array are in the same table.

The most important caveat in this report. patch_back2back scores 87.2 with two elements, while spacing0.6 scores 56.9 with sixteen. That is not because the small array performs better. Its potential is only 8.1 dB of output SINR — a low bar, easily reached. The 16-element array's potential is 31.3 dB, and reaching 57% of that is a much harder task left much less finished. A high closeness score does not mean good absolute performance.

Result 2 — the algorithm built for this case was not running

P8 added an anticipatory nuller specifically for on/off jammers: learn the toggle period from a presence indicator, then pre-form the null just before the jammer returns. Measured per toggle period, the branch fired on at most 1.3% of steps and never at all outside 10–15 s. Two independent causes, neither of which is a tuning problem:

  • Slow toggling (≥ 20 s) — the window is too short. The analysis buffer is 1024 steps = 51.2 s, and three cycles must fit inside it, so any period above ~17 s can never be trusted. Arithmetic.
  • Fast toggling (≤ 5 s) — presence saturates at 100%. The covariance horizon is 0.5 s but the OFF phase is 1–2.5 s, so the covariance still carries jammer energy and the eigengap never collapses. The presence signal the periodogram consumes is itself low-pass filtered by the beamformer's own forgetting factor. A constant signal has no spectral line, so no period is ever found.

The second is the more interesting: one forgetting factor was serving two jobs with opposite requirements. The beamformer wants a long memory for low variance; the on/off detector wants a short one to see edges. The repair gives the detector its own covariance.

The regression, traced to its actual cause

All 27 regressing cells are at the 4 s period. Two plausible explanations were tested and both refuted by measurement:

  • Mis-timed pre-null? No. Shortening the detector's memory improves presence error 0.30 → 0.15 → 0.09 while the score stays at exactly 80.1.
  • Pre-null firing too often? No. Halving the firing rate 4.7% → 2.5% leaves the score at exactly 80.1.

The real cause is a policy that had never executed. With presence saturated, the predictor never reached its "jammer absent" branch — it silently behaved as the reactive tracker. Fixing presence exposed that branch for the first time, and it releases the null and returns to the quiescent beam during OFF. At a 4 s period the OFF window is 2 s and turn-ons are frequent, so re-acquiring the null costs more than the extra gain buys. Recovery time after turn-on confirms it: 5.0 steps → 9.2 steps at that period.

A gate was built for it, measured, and left off

Releasing only after the jammer has been absent for several covariance horizons removes every regression cleanly — the worst ManyDipoles cell goes 66.4 → 93.5, matching the reactive baseline. But it costs the wins: a hard 10 s cell falls 59.8 → 39.8. The reason is structural. During OFF the perfect-knowledge reference sits at full quiescent gain, so every step spent holding the null scores zero — and any fixed threshold holds through the first N steps of every OFF window, including the long ones where releasing is right.

One constant cannot serve two regimes. This is the same shape as the forgetting-factor finding from the drift work: short OFF windows want the null held, long ones want it released, and a single threshold cannot do both. The honest resolution is a smooth, confidence-weighted release rather than a binary one — recorded as R2, not attempted here.

Result 4 — arrays that cannot do the job, and now say so

Two arrays previously crashed the entire Mode C stack, including the reactive tracker that has nothing to do with the predictive path. The cause was an opt-in feature (data-driven loading) whose precondition threw instead of degrading, and MUSIC's hardcoded source count. Both now degrade with a warning.

The Dipole result is the one worth pausing on: it scores 100.0, with mean SINR 5.92 dB against an oracle of 5.92 dB. With one element there is no spatial degree of freedom, so the quiescent beam is the optimum. The metric correctly reports that the array reached its potential — and its potential is to do nothing. That is exactly the behaviour a general-purpose algorithm should have.

Beyond running at all, the geometry preflight now refuses cells that are not real tests: 11 of 35 (array, target) pairs, each with a stated reason. All five Dipole targets are refused, because a 1-element beam covers the sphere and no jammer position lies outside the main lobe.

Findings

O-F1

Two defects made the stack unusable on small apertures

An opt-in loading feature threw rather than degrading, taking the reactive tracker down with it; and MUSIC's hardcoded source count (2·n_comp) threw on any array with too few elements. The first is pure downside — an earlier campaign measured that feature at +0.00 pp on all 90 cells, so it bought nothing anywhere and cost two arrays entirely.

O-F2

The global guard sector is wrong on every array

Derived per (array, target) it spans 16°–72.5° against a shipped constant of 5°. Any earlier result whose jammer sat between the true and the assumed guard was measuring a jammer inside the main beam — out of scope by the milestone's own definition.

O-F3

Detection quality and outcome are not the same thing

The repair improves presence error by 3–4× at every period, yet the score moves in opposite directions on different arrays. Two candidate explanations for the regression were falsified by finding the score invariant to the knob being swept — which is what pointed at the release policy instead. Worth keeping as a method: when a metric refuses to move, the cause is elsewhere.

O-F4

A campaign-length limit on what the predictor can show

Period learning needs three cycles, and runs here are four cycles long — so roughly 75% of each run is spent before a period exists. A fielded system sees many more cycles, so these numbers understate the anticipatory benefit and overstate the learning cost. Longer runs are the cheapest way to sharpen this.

O-F5

Process: algorithm modules were edited while a campaign was in flight

MATLAB reloads changed functions on the next call, so an edit made at ~case 137 could have split the arm in two. Neutralised by defaulting the new gate to inert and verifying the new code reproduces the pre-edit numbers exactly on five probe cells. The arm is homogeneous — but the right rule is simply not to edit modules mid-campaign.

Recommendations

  1. Derive the guard sector per (array, target); retire the global constant

    It is wrong on every array measured, by factors of 3 to 14. This is a one-line configuration change backed by kpi_array_profile, and it also supplies the feasibility check that lets an infeasible cell be reported rather than scored.

    Cheap · do first

  2. Replace the binary release policy with a graded one

    Hold-versus-release is currently all-or-nothing and a single threshold provably cannot serve both short and long OFF windows. Relaxing the null progressively with elapsed absence — or weighting by detection confidence — should capture most of both. This is the single change most likely to make the repair safe to enable by default.

    Moderate · highest value

  3. Do not enable the on/off repair by default yet

    It is a clear win on three arrays and a clear loss on one. Until R2 removes the regression, ship it opt-in — which is how it stands — and enable it per deployment once the array and the expected toggle rate are known.

    Free · a decision, not work

  4. Remove the data-driven loading feature, or make it earn its place

    Measured at +0.00 pp on all 90 cells of an earlier campaign, and it was the direct cause of two arrays being unable to run at all. It now degrades instead of throwing, but a feature with no measured benefit is carrying risk for nothing.

    Cheap

  5. Re-run with longer scenarios before judging the anticipatory path

    Four cycles per run means most of each run is spent learning. Ten-plus cycles would show what the predictor does once converged, which is the regime a fielded system actually occupies.

    Compute only

  6. Give MUSIC a rank-aware source count

    n_sig = 2·n_comp is an assumption, not a measurement. It makes MUSIC impossible on small dual-polarization apertures and mis-reads presence on arrays whose second component is weak but real. Estimating the model order from the eigenvalue profile would remove a whole class of array-specific failure.

    Moderate

Reproducing this

Both repairs ship disabled: the adapt.predict.onoff block is absent from config.yaml, and with it absent the code path is byte-identical to before. The graceful-degradation fixes (O-F1) are always on — they only replace a crash with a warning.
