Anti-jam milestone · Phase O + O2 · updated 2026-09-12

The on/off jammer, across every array we have

A stationary jammer that switches on and off, tested on every exported array. The predictive algorithm built for exactly this case turned out never to be firing. This is the diagnosis, the repair, a second campaign that reverses the first campaign's recommendation, and a graded release policy that was built, measured, and rejected. A final sweep over signal and jammer amplitudes then found that the residual gap to the achievable bound is driven by the strength of the wanted signal, not the jammer's — which moves the next work item off this algorithm entirely.

Arrays 7 (5 testable, 2 degenerate) Runs 1,782 + 2,430 closed-loop, 0 failed Gates 59/59 Status repair now ON by default Coherence span 0.06 – 0.98

Verdict

01

The on/off algorithm was never actually running

Its anticipatory branch fired on at most 1.3% of steps, and never at all outside a narrow 10–15 s band. Two independent causes, both arithmetic rather than tuning. Repaired, it fires 1.4–4.7% of steps and presence error against the true duty cycle falls from 0.46 to 0.13.

02

Every array now runs; two of them can't be helped, and say so

A 1-element and a 2-element array previously crashed the whole stack. They now run, and the geometry check reports 11 of 35 (array, target) pairs as infeasible with a stated reason — no gain, or a main beam covering the sphere — rather than scoring them as failures.

03

Enable it — a longer re-run reversed the earlier recommendation

Phase O measured a regression on the coarse-grid array and advised against enabling. That was a run-length artifact: period detection needs 3 cycles, and those runs were only 4 long. Re-run at 8 cycles the repair improves or ties on every array — mean 73.5 → 80.6, cells at the pass mark 24 → 32 of 90.

04

The graded release was built, measured, and rejected — and it closes the question

Relaxing the null continuously instead of dropping it scores 76.1 against the binary policy's 80.6, worse on 45 of 90 cells. It does rescue the binary tail, but a perfect per-cell choice between the two is worth only +0.9 and zero extra passing cells — so no release policy is worth further work.

05

What is left on the table is a calibration problem, not a nulling problem

Sweeping the amplitudes independently: raising the jammer by 20 dB costs almost nothing, while raising the wanted signal by 20 dB opens a gap to the achievable bound of up to 9.7 dB. That is the MPDR self-cancellation signature under steering mismatch. Every remaining decibel we can name sits here — and none of it is reachable by tuning the on/off logic.

What was tested, and how difficulty was made comparable

A stationary jammer at a fixed direction, switching on and off at 50% duty. Three axes were swept that no previous campaign had touched.

Target direction — never varied before

Every campaign to date fixed the target at (θ 90, φ 260). Measured across the seven arrays, quiescent directivity toward a target swings about 18 dB and the −3 dB beamwidth spans 24° to 120°. Target direction is a difficulty axis in its own right. On the mirror-degenerate array, (90, 260) is additionally the symmetry plane — that array's single most favourable target.

Separation in units of each array's own beam

A jammer 20° from the target is trivial for a 20-element array and inside the main lobe of a 6-element one. Separations are therefore set as multiples of a derived guard sector — half the wider beamwidth toward that target — so the same three numbers mean the same physical difficulty on every array.

The shipped guard_deg = 5 is wrong on every array. Derived per (array, target) it ranges 16° to 72.5°. The global constant was calibrated once, from one array's 15° beamwidth, and does not survive contact with a 120° beam. This is test infrastructure, applied identically to both arms, so it does not confound the comparison — but it invalidates the geometry of earlier campaigns that used the global value.

Result 1 — how close each array gets to its own potential

The score is the fraction of the run spent within 3 dB of a perfect-knowledge beamformer on that array, at that geometry. It asks "did we get what this aperture can give", not "did we hit an absolute number" — which is the right question when a 1-element array and a 20-element array are in the same table.

The most important caveat in this report. patch_back2back scores 87.2 with two elements, while spacing0.6 scores 56.9 with sixteen. That is not because the small array performs better. Its potential is only 8.1 dB of output SINR — a low bar, easily reached. The 16-element array's potential is 31.3 dB, and reaching 57% of that is a much harder task left much less finished. A high closeness score does not mean good absolute performance.

Result 2 — the algorithm built for this case was not running

P8 added an anticipatory nuller specifically for on/off jammers: learn the toggle period from a presence indicator, then pre-form the null just before the jammer returns. Measured per toggle period, the branch fired on at most 1.3% of steps and never at all outside 10–15 s. Two independent causes, neither of which is a tuning problem:

  • Slow toggling (≥ 20 s) — the window is too short. The analysis buffer is 1024 steps = 51.2 s, and three cycles must fit inside it, so any period above ~17 s can never be trusted. Arithmetic.
  • Fast toggling (≤ 5 s) — presence saturates at 100%. The covariance horizon is 0.5 s but the OFF phase is 1–2.5 s, so the covariance still carries jammer energy and the eigengap never collapses. The presence signal the periodogram consumes is itself low-pass filtered by the beamformer's own forgetting factor. A constant signal has no spectral line, so no period is ever found.

The second is the more interesting: one forgetting factor was serving two jobs with opposite requirements. The beamformer wants a long memory for low variance; the on/off detector wants a short one to see edges. The repair gives the detector its own covariance.

The regression, traced to its actual cause

All 27 regressing cells are at the 4 s period. Two plausible explanations were tested and both refuted by measurement:

  • Mis-timed pre-null? No. Shortening the detector's memory improves presence error 0.30 → 0.15 → 0.09 while the score stays at exactly 80.1.
  • Pre-null firing too often? No. Halving the firing rate 4.7% → 2.5% leaves the score at exactly 80.1.

The real cause is a policy that had never executed. With presence saturated, the predictor never reached its "jammer absent" branch — it silently behaved as the reactive tracker. Fixing presence exposed that branch for the first time, and it releases the null and returns to the quiescent beam during OFF. At a 4 s period the OFF window is 2 s and turn-ons are frequent, so re-acquiring the null costs more than the extra gain buys. Recovery time after turn-on confirms it: 5.0 steps → 9.2 steps at that period.

A gate was built for it, measured, and left off

Releasing only after the jammer has been absent for several covariance horizons removes every regression cleanly — the worst ManyDipoles cell goes 66.4 → 93.5, matching the reactive baseline. But it costs the wins: a hard 10 s cell falls 59.8 → 39.8. The reason is structural. During OFF the perfect-knowledge reference sits at full quiescent gain, so every step spent holding the null scores zero — and any fixed threshold holds through the first N steps of every OFF window, including the long ones where releasing is right.

One constant cannot serve two regimes. This is the same shape as the forgetting-factor finding from the drift work: short OFF windows want the null held, long ones want it released, and a single threshold cannot do both. The honest resolution is a smooth, confidence-weighted release rather than a binary one — recorded as R2, not attempted here.

Result 4 — arrays that cannot do the job, and now say so

Two arrays previously crashed the entire Mode C stack, including the reactive tracker that has nothing to do with the predictive path. The cause was an opt-in feature (data-driven loading) whose precondition threw instead of degrading, and MUSIC's hardcoded source count. Both now degrade with a warning.

The Dipole result is the one worth pausing on: it scores 100.0, with mean SINR 5.92 dB against an oracle of 5.92 dB. With one element there is no spatial degree of freedom, so the quiescent beam is the optimum. The metric correctly reports that the array reached its potential — and its potential is to do nothing. That is exactly the behaviour a general-purpose algorithm should have.

Read the table across, not down. Moving from the first column to the second raises the jammer by 20 dB and costs at most 2 dB, usually far less — the nulling is doing its job. Moving from the second column to the third raises the wanted signal by 20 dB and opens a gap of 9.7 dB on spacing0.6 and 3.5 dB on the patch array. The oracle rises with σs because it is handed the true steering vector; the algorithm does not, because it is not.

The size of the effect is strongly array-dependent, and that is the part still unexplained. The achievable value rises by exactly 20 dB on all four arrays, as it must. Of that 20 dB the algorithm captures 11.9 dB on spacing0.6, 17.3 on the patch array, and 19.7 / 19.8 on ManyDipoles and Monopoles — essentially all of it. The worst case is the highest-directivity array, which is consistent with mismatch (a narrow beam pays more for the same angular error), but four arrays at one geometry each is an observation, not a controlled sweep. This is finding O-F6 below, and it is the reason the top recommendation changed.

Phase O2 — the graded release, and a reversal

Phase O ended with two open items: a binary release policy that provably could not serve both fast and slow toggling, and a suspicion that four toggle cycles per run was too short to judge an algorithm needing three cycles to learn a period. One campaign addressed both: 90 cases × 3 seeds × 3 algorithms × 3 arms at 8 cycles — 2,430 runs, 0 failed case-seeds.

What the graded release does

Instead of dropping the null the instant the jammer is declared absent, it relaxes it continuously through diagonal loading — the physical knob that trades null depth for main-beam gain. Raising the load toward the scale of the covariance's own energy progressively swamps the jammer eigenvalue and returns the beam to quiescent. That was chosen over blending two beamformer solutions, which are defined only up to a phase and can cancel each other. Once the period is learned the ramp sizes itself to complete inside a fraction of the predicted OFF window, so it is short relative to a long gap and never completes inside a short one.

The graded release is worse, and that is the result

Paired against the binary policy it is −4.46 mean, worse on 45 of 90 cells, and it loses at every toggle period. It does exactly what it was designed to do — on the 11 cells where the binary policy regresses, binary averages −7.06 and graded +0.18, turning a −25.5 worst case into +0.2 — but it pays far more for that on the 79 cells that were never the problem.

Why the tuning misled me. The ramp was tuned on a five-cell probe hand-picked as conflict cells: three fast-toggle regressions against two long-period wins. That is a 60/40 split of a population that is really 11/79. The graded policy's cost falls on the majority and its benefit on the minority, so a curated conflict set over-weighted precisely the cells that motivated the change. The cheap guard, not applied: weight a tuning set by the population's own incidence before trusting it.

And the question is now closed

Taking the better of {no repair, binary} per cell — an oracle no real switching rule could beat — scores 81.5 mean / 32 passing against the binary policy's 80.6 / 32. The entire family of switching, hybrid and confidence-weighted release policies is therefore bounded at +0.9 mean and zero additional passing cells. The graded release was worth building to establish that bound; the bound says stop. Remaining effort belongs in detection quality, MUSIC's model order, and calibration — not in deciding when to drop the null.

The reversal

Phase O reported the repair regressing the coarse-grid array 83.0 → 79.7 and advised against enabling it. At 8 cycles that becomes 73.6 → 77.8, and the repair improves or ties on every array. The earlier finding was a run-length artifact, exactly as O-F4 predicted: with period detection needing 3 cycles, a 4-cycle run spends most of itself before a period exists. The recommendation is reversed and the repair is now enabled by default. Recovery after turn-on improves too — 14.7 → 9.7 steps at a 10 s period, 25.1 → 16.5 at 25 s.

Where the graded policy is still the right choice. On the coarse-grid array at a 4 s toggle period it is decisively better — the binary policy costs −25.5 there and graded costs +0.2. It ships as a documented, defaulted-off option for a deployment known to face fast toggling on such an array.

Findings

O-F1

Two defects made the stack unusable on small apertures

An opt-in loading feature threw rather than degrading, taking the reactive tracker down with it; and MUSIC's hardcoded source count (2·n_comp) threw on any array with too few elements. The first is pure downside — an earlier campaign measured that feature at +0.00 pp on all 90 cells, so it bought nothing anywhere and cost two arrays entirely.

O-F2

The global guard sector is wrong on every array

Derived per (array, target) it spans 16°–72.5° against a shipped constant of 5°. Any earlier result whose jammer sat between the true and the assumed guard was measuring a jammer inside the main beam — out of scope by the milestone's own definition.

O-F3

Detection quality and outcome are not the same thing

The repair improves presence error by 3–4× at every period, yet the score moves in opposite directions on different arrays. Two candidate explanations for the regression were falsified by finding the score invariant to the knob being swept — which is what pointed at the release policy instead. Worth keeping as a method: when a metric refuses to move, the cause is elsewhere.

O-F4

A campaign-length limit on what the predictor can show

Period learning needs three cycles, and runs here are four cycles long — so roughly 75% of each run is spent before a period exists. A fielded system sees many more cycles, so these numbers understate the anticipatory benefit and overstate the learning cost. Longer runs are the cheapest way to sharpen this.

O-F5

Process: algorithm modules were edited while a campaign was in flight

MATLAB reloads changed functions on the next call, so an edit made at ~case 137 could have split the arm in two. Neutralised by defaulting the new gate to inert and verifying the new code reproduces the pre-edit numbers exactly on five probe cells. The arm is homogeneous — but the right rule is simply not to edit modules mid-campaign.

O-F6

The residual gap is a strong-signal effect, and it is the largest number left

Raising the jammer 20 dB costs almost nothing; raising the wanted signal 20 dB opens up to 9.7 dB against the achievable bound. The mechanism is not in doubt: this solver is MPDR, so the wanted signal is inside the estimated covariance, and under any steering mismatch the solution spends degrees of freedom cancelling it — the stronger it is, the more there is to cancel. The oracle does not suffer, because it is handed the true steering vector. Two consequences. First, every campaign number in this report is a weak-signal number (σs = 0 dB) and therefore flatters the stack relative to a strong-signal deployment. Second, the gap is invisible to any amount of on/off tuning, which is why it displaces the guard sector at the top of the recommendations. What is not established is why the loss ranges from 8.1 dB to 0.2 dB across four arrays; the highest-gain array is worst, which fits the mismatch story, but confirming it needs a mismatch × σs sweep rather than the four single-geometry probes run here.

Recommendations

  1. Attack the steering mismatch — it is where the remaining decibels are

    Up to 9.7 dB against the achievable bound in the strong-signal regime (O-F6), against the +0.9 dB a perfect release policy was worth. The standard remedies are well understood and cheap to try in this order: diagonal loading swept against mismatch rather than against null depth; a derivative (point-and-null) constraint widening the protected region around θs; and, if those fall short, robust Capon with an explicit uncertainty ellipsoid. Measure it with the amplitude grid, not the existing campaign — the campaign runs at σs = 0 dB and structurally cannot see this effect.

    Moderate · highest value · do first

  2. Derive the guard sector per (array, target); retire the global constant

    It is wrong on every array measured, by factors of 3 to 14. This is a one-line configuration change backed by kpi_array_profile, and it also supplies the feasibility check that lets an infeasible cell be reported rather than scored.

    Cheap · do alongside

  3. Replace the binary release policy with a graded one — done, and rejected

    Built and measured at scale: 76.1 against the binary policy's 80.6, worse on 45 of 90 cells. It rescues the binary tail but costs more elsewhere, and a perfect per-cell choice between the two is worth only +0.9. No release policy is worth further work — that bound is the useful output of having built it.

    Closed · negative result

  4. Do not enable the on/off repair by default yet — done, and reversed

    Superseded by Phase O2. Re-run at 8 cycles the repair improves or ties on every array (mean 73.5 → 80.6, passing 24 → 32), so it is now enabled by default in config.yaml.

    Closed

  5. Remove the data-driven loading feature, or make it earn its place

    Measured at +0.00 pp on all 90 cells of an earlier campaign, and it was the direct cause of two arrays being unable to run at all. It now degrades instead of throwing, but a feature with no measured benefit is carrying risk for nothing.

    Cheap

  6. Re-run with longer scenarios before judging the anticipatory path

    Four cycles per run means most of each run is spent learning. Ten-plus cycles would show what the predictor does once converged, which is the regime a fielded system actually occupies.

    Compute only

  7. Give MUSIC a rank-aware source count

    n_sig = 2·n_comp is an assumption, not a measurement. It makes MUSIC impossible on small dual-polarization apertures and mis-reads presence on arrays whose second component is weak but real. Estimating the model order from the eigenvalue profile would remove a whole class of array-specific failure.

    Moderate

Reproducing this

Shipping state, as of this revision: the adapt.predict.onoff block is enabled in config.yaml (verdict 03 reversed Phase O), and the graded-release block ships beside it commented out (verdict 04). Remove the onoff block and the code path is byte-identical to the pre-Phase-O behaviour — that is the contract the opt-in gates enforce. The graceful-degradation fixes (O-F1) are always on; they only replace a crash with a warning.
